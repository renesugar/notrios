# v0.5 E9 — Documentation and release wrap-up

Status: complete on 2026-08-06.

Model: Claude Opus 5 (Claude Code).

## What it does

Closes v0.5: version 0.5.0, the documentation site and Help notebook caught up
with everything E1–E8 shipped, the living documents reconciled against the
source tree, a v0.5.0 release checklist, the plan archived, and the v0.6 plan
drafted from `ROADMAP.md`.

## What reconciliation actually found

A wrap-up slice earns its place by finding the things nobody noticed while
shipping. Five, in rough order of how much they mattered.

**Three v0.5 roadmap bullets did not ship.** `ROADMAP.md` listed *templates and
task extraction* and *graph visualization and path finding* under v0.5. The
first two never entered `PLAN.md` as a task at all — thirteen slices went by
without anyone noticing. The third half-shipped: E4 delivered traversal, paths,
and the orphan/hub report and named itself "traversal, paths, and
**visualization data**" precisely because there is no graph view in the GUI.

All three moved to v0.6 explicitly — in `ROADMAP.md`, in `FEATURE_MATRIX.md` as
rows with a status, and in the release checklist's known boundaries. The
alternative was leaving a roadmap that quietly disagrees with the code, which is
the failure mode this slice exists to catch.

**Two `ROADMAP.md` v0.6 bullets are already implemented.** "LLM-safe surgical
edits with dry-run and revision preconditions" and "LLM-safe SEARCH/REPLACE
edits" are both the existing `edit_note` tool and
`PATCH /api/v1/documents/{id}`, complete since the v0.2 redesign. The v0.6 draft
records them under "already implemented, deliberately not re-listed" rather than
restating them as work — a plan that lists finished work as pending makes the
milestone look larger than it is and invites someone to re-do it.

**The MCP guide disagreed with the registered tool list.** `docs/api/mcp.md`
omitted `scan_remote_media` from the read tools and `localize_remote_media` from
the write tools. Both are registered and callable. Fixed by reading the tool
names out of `internal/httpapi/mcp.go` rather than trusting the prose.

The same page now carries what MCP deliberately does *not* expose — lint, fix,
graph, blocks, query blocks, tag rename, notebook deletion and its preview, GC,
archive export/verify/restore, publication — stated as a standing decision. That
list was previously only inferable by noticing the absence, which is the same
shape of problem as the missing tools: silence read as either.

**`docs/operations.md` opened with "This guide covers the v0.3 workflows".**
Two milestones stale, on a page that had since grown lint, fix, the graph
report, and (in this slice) tag rename and notebook deletion. Rewritten around
the two rules the page actually follows: reports never write, and anything that
writes is a dry run by default.

**E7 and E8 were absent from the site and the Help notebook.** Both had updated
the design and policy documents but not the user-facing pages —
`POST /api/v1/note-queries/run` had no REST guide entry at all, and E8's
surfaces had none anywhere. Because `notriosctl seed-help` mirrors `docs/`, a
gap in the site is a gap in the offline Help notebook too.

## Decisions worth recording

**The v0.6 plan's third constraint is new.** v0.5 carried two: nothing
unbounded, and note content is untrusted. v0.6 adds *a tool's reach is declared,
not inferred* — a tool hidden from `tools/list` must also be refused when called
directly, by construction rather than by remembering. That is the difference
between hiding a tool and not granting it, and F2 is where it has to be settled.

**Slices with no scale profile now say so in one place.** E1b, E3, E6b, E7, and
E8 each recorded a written reason in their archived plan; the README and the
release checklist now point at that rather than leaving a reader to wonder why
`performance/v0.5-*` has seven directories and not thirteen.

## Validation

Full release-candidate suite: `go vet ./...`, `go test ./...`, required-file,
plan-loop, and scaffold checks, OpenAPI parse, migration-copy equality, web
lockfile install, typecheck, tests, and production build, `make gui`,
documentation-site build, deterministic Help-notebook seed and reseed,
end-to-end REST/MCP smoke, generated store performance smoke, the offline-assets
check, and a source ZIP produced by `scripts/package_release.sh` and
independently verified by `scripts/check_release_zip.py`.

The Help reseed is run twice on purpose: the second run must report every note
kept and none updated, which is what makes the seed deterministic rather than
merely idempotent-looking.
